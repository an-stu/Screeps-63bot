## 踩坑与工具

- Screeps 控制台 API：**表达式只能是单条 `return ...`**；多条语句会被静默丢弃。需要多行逻辑必须写成 `return (function(){ ... })()`。表达式整串长度上限在 850~1050 字符之间。
- 控制台输出走 socket，REST 取不到；正确做法是用 `Memory.__probeN = ...` 回传，再用 `/api/user/memory?path=...` 读回（返回值可能是 `gz:` + base64 的 gzip）。且主循环会把自己缓存的 Memory 换回 `global.Memory`，约有半数写入被丢弃，必须重试。
- 运行时插桩：`global.X` 上的对象在代码重载前一直存在，可以直接包裹函数做计时，不用改代码。
- ~~**`TeamRaL1.execSpawn` 的卡死缺陷**~~ —— **更正：这是设计，不是 bug。** 出兵条件是
  `!flag.memory.creepName || (name 含 "_keeper" && spawnTime+1450-concatTime < Game.time)`：
  - 不带 `_keeper` = **一次性旗**，只出一只，爬死后不补（`raL1_E59S38_1` 属于这种，属正常用尽）。
  - 带 `_keeper` = **持续旗**，在旧兵死前 `concatTime`（= 线性距离 × 50）出兵接力。
  - 复查用过的非 keeper 旗要手动 `delete flag.memory.creepName`。
- **改名会杀兵**：`UtilsTask.taskFlag` 把 task.id 设为 `flag.name`，而 `Creep.prototype.raL1` 首行是
  `if (!flag) this.suicide()`。所以爬活着时不能重插旗子换名（想改 `_keeper` 得等这批爬死完）。

## v0.78.42 — 外矿矿物链：四个独立缺陷，全服 0 只 harvestMineralOuterKeeper

起因：查 W34N55（W33N55 的外矿、中间九房 Source Keeper 房）时发现 35000 的 H 从未被
动过，而全账号 `harvestMineralOuterKeeper` 数量是 **0**。顺链查下去是四个各自独立、
任一都能让整条链死掉的缺陷：

1. **`trySpawnOuterMineralKeeper` 在 mineral 周围「每一格非墙格子」都放 container 工地**
   （9 格循环、`createConstructionSite` 后没有 break）。W34N55 实测 9 格里 5 格是墙、
   正中那格是 mineral 自己，于是落下 **3 个**工地 (42,15)/(43,15)/(43,16)，15000 的
   工程量没人修得完，另外两个永久占工地配额。
2. **工地存在时派的是 `worker` 且 tasks 是空数组** —— 在主房出生、没有任务，只会修主房
   自己的工地，永远不走外矿房。于是容器永远 0/5000；而矿爬的生出条件又是 `container`
   存在，所以矿爬也永远不生。连锁死。
3. **`harvestMineralOuterKeeper` 读错 Memory 路径**：
   `Memory.rooms[room].stationSources[mineralId]`，但矿物记录在 `stationMineral`
   （一房一条、不按 id 分桶）→ 拿到 undefined → 下一行 `station["container"]` 必抛
   TypeError。**这是潜伏的崩溃**，只因为矿爬从没生出来才没炸。
4. **`generatorOuterMineTask` 的 regFun 是 `registerStationSources`**，把矿物 id 写进
   `stationSources[mineralId]`；`trySpawnOuterHarKeeper` 遍历 stationSources 找 `id`，
   会把矿物当成矿点、给它派 harvestEnergyKeeper。

另外**外矿矿物完全没有搬运链**（全库搜不到第二个 MineralOuter / 矿物 carrier）：矿爬是
`{MOVE:15,WORK:30,CARRY:4}` 的固定采集爬只填容器，`trySpawnOuterHarCarrier` 只遍历
stationSources 不看 stationMineral → 容器满了 H 就永远堆在外矿。

修法：`ensureOuterMineralContainerSite` 只选一格（跳过 mineral 自己那格与墙，挑周围
可走格最多的），并顺手收敛历史多工地；新增 `outerMineralContainerBuilder`
（`{WORK:16,CARRY:17,MOVE:17}`，任务是**自循环**：空了就 push 一条回主房 storage 的
`carryRes`，取完自己 pop，下一 tick 回到本任务继续修 —— 5000 进度、1 能量换 1 进度、
一趟最多带 850，一趟修不完）；新增 `harvestMineralOuterCarry`（`{CARRY:25,MOVE:25}`
往返 1250/约 160 tick，比让矿爬自己搬快 6 倍，且只在矿爬已在场时才派）。

验证：3 个工地收敛到 1 个 (43,15)、`containerSite` 已入 Memory、builder 按设计体型出生
并**装满 850 能量出发**、矿物容器已修到 1700/5000。

### 修路/搬运的启动顺序（重要，别再踩）

`trySpawnOuterHarCarrier` 的生出条件是 `data["container"]`，而**路是 carrier 走路时
边走边铺的**（`harvestEnergyOuterCarryRoadBuilder` 里 `createConstructionSite(ROAD)`）。
所以**新外矿房在第一个容器建成前一条路都没有**。W34N55 实测：容器 @32,31 建成后
carrier 才出生、才开始铺路。想让路更早，就得把 carrier 的门槛从「容器建成」放宽到
「容器工地存在」。
