## 外矿 W34N55 复查：三个让外矿半瘫的问题

隔夜复查，用户反馈「road 完全没修好 / 自己爬有时候会死 / mineral 没有 container」。

### 1. defenser 根本生不出来（最严重）

`getOuterHarDefenseBodyConfig` 调用了 `e.possibleToughBeHitsDamage(sumHeal)` ——
**这个方法全代码库不存在**。于是**只要房间里看得见 keeper 就抛 TypeError**，
`trySpawnOuterDefenser` 整个挂掉。W34N55 实际只维持 1 只 defenser，第二只
只在「刚好没敌人」的那一瞬才生得出来。同一处坏写法在
`strategy_defenserHighWay.js:51` 也有（那是老代码，我上次照抄了这个模式）。

替换成 `WarDamageCal.possibleBreakDamage(creep, sumHeal)`
（`BREAK_TICKS=12` 标定：keeper 约 5000 血 + 17 TOUGH → 559/tick → 19 ATTACK，
加抗压部件后刚好落在 50 部件内，与手工调好的 {ATTACK:22,HEAL:11,MOVE:17} 一致）。
顺手补了 `hitsOnTough`（`war_damageCal.possibleDamage` 引用了它但从未定义）。

另外自适应体型**偏小**：它按 `possibleDamage(false, 2)` 只算远程，实战一贴身
奶量就不够 —— 实测算出 16 ATTACK / 5 HEAL，而真正打赢的是 22 / 11。
现在入侵房（isInvader）一律不低于 bigBody。

### 2. lair 分组按坐标排序是错的，要按寻路距离

实测 W34N55 四个窝之间的**真实 path 长度**：

```
(36,29)-(41,14)  14
(7,38)-(36,29)   26
(41,14)-(7,38)   39
(7,17)-(41,14)   42
(7,17)-(36,29)   58
(7,17)-(7,38)    83   ← 直线只差 21，中间有墙要绕
```

按 (x,y) 排序对半切 → {(7,17),(7,38)}=83 + {(36,29),(41,14)}=14，合计 **97**。
最优配对 → {(7,17),(41,14)}=42 + {(7,38),(36,29)}=26，合计 **68**。

`outerDefenseLairGroups` 现在做**最小权两两配对**（枚举所有配对，n≤6 够用），
结果按 lair id 集合缓存进 `room.memory.defenseLairGroups`，只算一次。
另外把「守最快出怪那个」改成用户要的**两窝轮换**，停留时长按
`(300 - 2×路程)/2` 算（西组 116、东组 134），让往返一圈 ≈ lair 的 300 tick 周期。

### 3. 路卡在 34 条的真实原因

两个叠加原因：
- 缓存路线被**单次移动失败就整份删掉**（三处：`harvestEnergyOuterCarryRoadBuilder`、
  `moveOuterCarrierOnRoad`）。这份缓存是**同矿点所有爬共用**的，任何一只被挡一下
  就全没了。
- 重建路线的唯一入口 `ensureOuterRoadPath` 挂在 `trySpawnOuterHarCarrier` 里，
  而那个函数开头就被 `spawnFailure` 挡住 —— 主房 spawn 常年忙，路线长期缺失，
  **路点根本铺不下去**。

改法：失败要连续 `OUTER_ROAD_FAIL_TOLERANCE`(100) tick 才作废；路线维护移到
`spawnFailure` **之前**（只对外矿房，主房不做寻路省 CPU）；路未完工时补到
`OUTER_ROAD_BUILDER_CNT`(3) 只带 WORK 的 carrier —— 修路吞吐被「每趟能带多少
能量」卡死（1 能量 = 1 进度），加大 CARRY/WORK 都没用，只能多几只同时跑。

## 补充：defenser 提前落位 + 修路的真正瓶颈（83301800 前后）

### defenser 改成「提前落位」（用户要求）

`keeperLair.ticksToSpawn` 本身就是**下一只 keeper 还有多久出窝**。现在 defenser 直接站到
组内**最快要出**的那个窝旁边（range 1）等：

- keeper 一出窝就扑最近的一只爬，defenser 已经贴着 → 最近的爬就是它自己 →
  keeper 会**原地跟它打**，8 tick 内被 22 ATTACK（660/发）打掉，**不会**跑去杀矿工。
- 反过来如果出窝时 defenser 不在（在另一个窝或路上），keeper 就一路去找矿工。
- 这个「守最快出怪的窝」天然实现了「杀完这只换另一只」：清掉后该窝倒计时重置回
  ~300，另一个窝立刻成为最小 → defenser 自己走过去，不需要额外轮换状态机。
- 组内两个窝都没倒计时（未激活）时才退回按 dwell 轮换，顺带把两个窝都唤醒。

实测：组0 (7,17) 倒计时 198 / (41,14) 288 → 去 (7,17)；组1 (36,29) 64 → 去 (36,29)，d=4。

### 路卡在 34 条的真正原因（第二次，才是根本）

上一次只修了「路线缓存被删 + 重建被 spawnFailure 挡」。真正让路**一格都不动**的是
立工地的条件：

```js
else if (this.ticksToLive > 300 && !pro.roadBlockedByBlueprint(this.pos)
    && !this.pos.lookFor(LOOK_CONSTRUCTION_SITES).length) {
    this.pos.createConstructionSite(STRUCTURE_ROAD)
}
```

实测那只修路 carrier **ttl 只剩 154** → 条件恒假 → **完全不再立工地**。而且一次只立一格：
必须正好站在缓存路点上，就算派 3 只 carrier 也没法并行，前一只没修完，后一只走到那儿
也不立。

改成新增 `placeOuterRoadSites(data, spawnRoom)`：按缓存路线**批量立工地**（跳过边界格、
已有建筑、已有工地、蓝图占位、主房自管路段），每 100 tick 一轮、每轮最多 30 个。
调用点排在 `cleanupOuterRoadSites` 之前、`spawnFailure` 之前。

**实测：部署后 W34N55 立刻出现 56 个道路工地（之前 0），与统计出的缺口 58 基本吻合。**
现在多只带 WORK 的 carrier 可以并行施工。

### 这轮学到的通用教训

**「立工地」和「修工地」是两件事，不要耦合在移动逻辑里。** 把立工地绑在「爬正好走到
那个路点、且寿命还够」上，会让整个工程在 carrier 寿命尾段、路径轻微偏移、或者
多次往返之间完全停摆，而日志里一点异常都没有。批量前置立工地 + 多个施工者并行，
既好观测（工地数量直接反映缺口）又能并行。
